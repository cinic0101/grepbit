- **Product version:** 0.2
- **Document revision:** 0.2.2
- **Status:** Implementation draft
- **Date:** 2026-09-08

## 1. How to use this document

Read `AGENTS.md`, then Sections 1 through 9 of this document before changing
production code. Sections 10 through 14 describe onboarding, the probe
north star, evaluation, delivery slices, and non-goals. The words MUST,
MUST NOT, SHOULD, and MAY are normative.

Authority order: user and harness instructions, `AGENTS.md`, this document,
accepted ADRs under `docs/adr/`, the retained v0.1 contracts, then code and
tests. If accepted evidence makes a statement here wrong, amend the statement
and bump the document revision.

## 2. Product statement

> Grepbit is a data agent that other agents call. Given a datasource with a
> reviewed semantic catalog, it turns one question into one structured query,
> executes it through deterministic safety and validation gates, and returns
> either a verified answer with its interpretation, assumptions, SQL, and
> evidence, or an honest, typed refusal that says what it would need.

The north star is a bounded **data probe sub-agent** (Section 11) that
investigates a hypothesis over several probe steps and returns a structured
report. Version 0.2 delivers the single-shot capability that every probe step
is built from.

Generality lives in onboarding: any PostgreSQL datasource can be registered
and given a catalog. The question space is bounded by the catalog, and the
product says so through `GET /capabilities` and through typed refusals.

## 3. Invariants

These hold in every slice. Violating one stops feature work until repaired.

1. The model never emits SQL, table or column identifiers outside the
   supplied catalog subset, or data-derived values. It may emit typed slot
   values that originate from the user's question (a month, a limit, an
   enumerated dimension value).
2. Every slot value is validated against its declared type and bound as a
   query parameter by the server. No value is interpolated into SQL text.
3. Reviewed semantics carry `review_state`. Candidate definitions may be used
   but every answer that depends on one is `unverified_semantics`, never
   `verified`.
4. Execution is read-only through the allowlisted PostgreSQL role, the
   SQLGlot policy gate, statement timeouts, and row limits.
5. Deterministic validators decide verification. Model output never creates
   verification state.
6. Assumptions and clarification options are generated by deterministic code
   from the catalog. The model only phrases them.
7. Result rows never enter a prompt. Bounded, redacted previews may appear in
   responses according to sensitivity policy.
8. Every answer is reconstructable from the evidence ledger: interpretation,
   assumptions, query record, parameters (typed, redacted), validations, and
   claims.
9. `false_verified_count` is zero in every evaluation run.
10. Secrets are environment references. Nothing reads, prints, or commits a
    credential.

## 4. Architecture

Dependency direction is unchanged:

```text
API -> application -> domain
          |
          v
        ports <- adapters
```

Adapters hold Wren, PostgreSQL, SQLGlot, SQLite, and Chat Completions
mechanics. Wren types stay inside `adapters/wren/`. PostgreSQL execution
belongs only to the psycopg adapter.

The v0.2 query path:

```text
question
  -> RequestGrounding
       fast path: reviewed literal match       (zero model calls)
       otherwise: candidate retrieval          (deterministic, catalog)
                  -> model classification      (one call, constrained)
                  -> server validation
  -> StructuredQuery                           (typed, value-bearing slots only)
  -> QueryRenderer                             (deterministic)
       -> Wren semantic SQL with placeholders
       -> parameter specs + server bindings derived from slots
       -> assumptions from definitions and defaults
  -> WrenSemanticEngine.compile()
  -> SqlPolicy.evaluate()
  -> PsycopgQueryExecutor.execute()
  -> validators
  -> evidence ledger
  -> AgentResponse
```

Terminal statuses that skip execution: `clarify`, `semantic_gap`,
`unsupported`, `unsafe`. Each is produced before any model call when the
deterministic stage can decide it, and otherwise after the single
classification call.

## 5. Semantic catalog

The catalog is the server-owned, value-free description of what can be
asked. It is loaded per datasource from a reviewed JSON or YAML document
whose revision and digest are recorded in run context.

```yaml
catalog_revision: retail_v1-catalog-v2
business_timezone: Asia/Taipei
models:                      # from the Wren MDL; grain and keys
  orders: {grain: order_id, time_fields: [ordered_at]}
metrics:
  recognized_revenue:
    description: Completed-order gross amount minus discount, excluding tax and returns.
    unit: TWD
    review_state: verified          # verified | candidate
    reviewed_by: product_owner
    synonyms: [revenue, recognized revenue, sales]
    ambiguity_group: revenue
    disambiguators: [recognized, net of discount]
    default_filters:
      - {dimension: orders.status, value_id: completed, assumption: "Only completed orders count."}
    null_policy: {field: orders.discount_amount, treat_as: 0, assumption: "A missing discount is zero."}
    supported_shapes: [metric_scalar, metric_by_dimension, metric_over_time, compare_periods, top_n]
  net_after_returns: {...}
dimensions:
  customers.customer_id: {type: text, review_state: verified, synonyms: [customer]}
  orders.status:
    type: enum
    values: [completed, cancelled]   # value ids the model may reference
    review_state: verified
time_fields:
  orders.ordered_at: {default: true, description: Order time in Asia/Taipei.}
sensitivity:
  customers.email: sensitive
unsafe_patterns: [delete, drop, copy, pg_sleep, ignore previous instructions, 刪除]
unsupported_patterns: [forecast, predict, 預測]        # request kinds outside the product
semantic_gap_patterns: [margin, profit, 毛利, 庫存]     # concepts known to be absent
```

Synonyms, disambiguators, and the three pattern lists may mix languages; the
lexical matcher applies word boundaries only where the script has words, so
Chinese phrases match inside longer strings. Adding a language is catalog data,
not code. Missing translations cost an extra clarification, never a wrong answer.

Rules:

- A metric MUST declare `review_state`. Only `verified` metrics with verified
  dimensions and time fields can yield `verified` answers.
- `ambiguity_group` members share user vocabulary. A question that matches
  the group but no member's `disambiguators` MUST produce `clarify` with the
  members as options.
- Enumerated dimension values are ids. The model references ids; the server
  binds the stored value.
- The catalog is the only source of identifiers the model may use. The
  reviewed retail_v1 definitions in
  `evals/fixtures/retail_v1/semantic/candidate_definitions.yaml` and
  `semantic/retail_v1/reviewed_query_contracts.json` are the first catalog.

## 6. Structured query

The model output contract for an answerable question:

```yaml
StructuredQueryProposal:
  shape: metric_scalar | metric_by_dimension | metric_over_time | compare_periods | top_n
  metric_id: recognized_revenue
  dimension_ids: []                 # by_dimension, top_n
  time_field_id: orders.ordered_at  # null uses the catalog default
  time_scope:                        # exactly one form
    month: {slot: "2026-07"}                       # ISO_MONTH
    range: {start: "2026-07-01", end_exclusive: "2026-08-01"}   # ISO_DATE
    relative: {unit: month, offset: -1}            # resolved from as_of by the server
    periods: [{month: "2026-07"}, {month: "2026-08"}]           # compare_periods
  filters:
    - {dimension_id: orders.status, value_id: completed}         # enum only in v0.2
  limit: 10                          # top_n, POSITIVE_INTEGER, server-capped
  order: desc
```

Rules:

- All ids MUST be members of the candidate subset supplied to the model.
- Slot kinds are `ISO_MONTH`, `ISO_DATE`, `POSITIVE_INTEGER`, `ENUM_VALUE_ID`,
  and `RELATIVE_PERIOD`. Free text filters are not supported in v0.2.
- Relative periods are resolved deterministically from `run_context.as_of`
  in the business timezone. The model never does date arithmetic.
- The renderer rejects a shape the metric does not support, a dimension with
  a grain conflict, or a missing required time scope, with a sanitized code.

## 7. Grounding

1. Normalize the question (NFKC, casefold, whitespace).
2. Fast path: if a reviewed request literal matches, materialize its
   structured query with zero model calls.
3. Pattern checks: `unsafe_patterns` terminates as `unsafe`,
   `unsupported_patterns` as `unsupported`, and `semantic_gap_patterns` as
   `semantic_gap`, all before any model call.
4. Candidate retrieval: whole-phrase synonym matching over the catalog yields
   candidate metrics; ambiguity-group siblings, dimensions of the base and
   related models, and base-model time fields are added. When an embedding
   port is configured, catalog entries are embedded once (document prompt) and
   the question once (query prompt, with dates and numbers neutralized);
   metrics scoring above the gap threshold and within the band of the best
   score join the candidates. Embedding scores select candidates; they do not
   decide the answer, and near-miss vocabulary above the threshold is refused
   by the classifier or by `semantic_gap_patterns`. Zero candidate metrics
   terminates as `semantic_gap` with the nearest metrics as suggestions. The
   retriever revision (lexical version, embedding model, prompt format, gap,
   band) is recorded on every decision.
5. Classification: one model call receives the question, `as_of`, and the
   candidate subset of the catalog (definitions without values). It returns a
   `StructuredQueryProposal`, or `{decision: none, reason}`. Output is
   validated with a JSON schema; invalid output is a typed model failure, not
   a retry.
6. Server validation: ids in the candidate subset, slots typed, shape
   supported, budget respected.
7. Ambiguity rule: if the chosen metric's `ambiguity_group` matched and no
   member disambiguator appeared in the question, return `clarify` with the
   group members as options, each carrying the structured query delta.
8. Interpretation echo: every answer restates the structured query in words
   so the caller can detect misrouting.

The model call budget for grounding is one. A second call is allowed only to
phrase a clarification or summary and never changes the structured query.

## 8. Response contract

`POST /ask` and the MCP tool return the same shape once the run completes.

```json
{
  "run_id": "run-...",
  "status": "answered | clarify | semantic_gap | unsupported | unsafe | failed",
  "interpretation": {
    "text": "Recognized revenue for July 2026 (Asia/Taipei), completed orders only.",
    "structured_query": {"shape": "metric_scalar", "metric_id": "recognized_revenue", "time_scope": {"month": {"slot": "2026-07"}}}
  },
  "assumptions": [
    {"text": "Only completed orders count.", "source": "reviewed", "definition_ref": "metrics.recognized_revenue.default_filters[0]"},
    {"text": "A missing discount is zero.", "source": "reviewed", "definition_ref": "metrics.recognized_revenue.null_policy"},
    {"text": "July 2026 is [2026-07-01, 2026-08-01) in Asia/Taipei.", "source": "default", "definition_ref": "time_fields.orders.ordered_at"}
  ],
  "clarification": {
    "question": "Do you mean recognized revenue or net revenue after returns?",
    "options": [{"label": "Recognized revenue", "query_delta": {"metric_id": "recognized_revenue"}}]
  },
  "result": {"columns": ["recognized_revenue"], "rows": [{"recognized_revenue": "290.00"}], "row_count": 1, "truncated": false},
  "sql": "SELECT ...",
  "verification": "verified | partially_verified | unverified_semantics | inconclusive | blocked",
  "validations": [{"validator": "semantic_definition", "status": "passed"}],
  "usage": {"model_calls": 1, "queries": 1, "wall_clock_seconds": 1.8},
  "evidence_url": "/runs/run-.../evidence"
}
```

Rules:

- `assumptions[].source` is `reviewed`, `candidate`, or `default`. Any
  `candidate` source forces `verification` to `unverified_semantics` or lower.
- `clarification` is present only when `status` is `clarify`; `result` and
  `sql` are present only when `status` is `answered`. A clarification carries
  `pending_query`, the validated query the classifier proposed, so the caller
  can resolve it by posting the same question with
  `clarification_choice: {run_id, metric_id}`; the server substitutes the
  chosen metric and executes with zero model calls
  (`grounding_path: clarification_resolved`).
- Sensitive columns are redacted in `result` and in `sql` per the retained
  redaction policy.
- `GET /runs/{run_id}` returns the stored `AgentResponse`.
  `GET /runs/{run_id}/evidence` returns query records, validations, relations,
  claims, and request grounding evidence; it exists only for asks that reached
  execution.
- `GET /capabilities` returns the value-free catalog: metrics with
  description, unit, review state, synonyms, supported shapes; dimensions with
  enumerated value ids; time fields; reviewed question templates as patterns.
- `GET /healthz` returns readiness, catalog revision and digest, retriever
  revision, and whether a classifier and embeddings are configured.

`POST /ask` is synchronous in v0.2: one question is bounded by the request
wall clock and the process serializes asks on one writer thread. Every ask is
recorded (run id, status, path, candidate ids and scores, retriever revision,
model calls, clarification choice) and, unless `GREPBIT_RECORD_QUESTIONS` is
false, the question text, so clarifications and gaps can be mined for
candidate synonyms and evaluation cases. The v0.1 asynchronous run lifecycle,
idempotency, cancellation, and datasource administration remain in the code
but are dormant until a slice needs them.

## 9. Trust tiers and budgets

| Verification | Condition |
|---|---|
| `verified` | All definitions reviewed, required validators passed, result complete |
| `partially_verified` | Reviewed definitions, result truncated or preview-limited |
| `unverified_semantics` | At least one candidate definition or default without review |
| `inconclusive` | A trap validator failed (fanout, grain, null denominator, time boundary) |
| `blocked` | Policy, safety, or budget terminal before execution |

Budgets reuse the retained `QueryBudget`. Defaults for v0.2: one query per
task, one model call for grounding plus at most one for phrasing, 30 second
statement timeout, 60 second request wall clock, 5,000 result rows, 100
preview rows. The fast path target is under 500 ms; the classified path
target is under 8 seconds P95 on the reference model.

## 10. Onboarding a datasource

v0.2 manual path:

1. Register the datasource with an environment secret reference and
   allowlisted schemas (retained v0.1 Section 10.6).
2. Introspect to obtain the catalog snapshot.
3. Author the semantic catalog document (Section 5) and the Wren MDL by hand
   or from a template. Validate with `grepbit catalog validate`, which
   compiles each metric shape through Wren, runs the SQL policy, and checks
   output schemas against the datasource without executing user questions.
4. Mark definitions `verified` only with a named reviewer.

v0.3 adds `grepbit catalog draft`, which uses the model to propose candidate
metrics, synonyms, and descriptions from the introspected schema and
comments. Drafts are `candidate` until reviewed.

## 11. North star: data probe sub-agent

Out of scope for v0.2. Recorded so that v0.2 decisions do not block it.

- Input: a hypothesis or phenomenon, scope hints, and a budget.
- Primitives: metric over time, breakdown by dimension, compare periods,
  top-N with drill-down through relation keys (G4), filter emptiness check,
  column profile, freshness and gap check. Each primitive is a reviewed
  template. The model chooses the next primitive and its slots; it never
  writes SQL.
- Loop: after each step, validators run, evidence is recorded, and the model
  sees a bounded summary, never rows. Budgets and stop conditions are server
  enforced (G5 ObservationDecision, reshaped).
- Report: findings with per-finding verification and assumptions, open
  questions, hypotheses to check (never causal claims), budget used, and
  suggested next probes.
- Ambiguity: probe both readings when cheap and report which was assumed;
  escalate to `clarify` only when readings diverge and budget forbids both.

## 12. Evaluation

Evaluation answers the product hypothesis. It is run once per meaningful
change and reviewed by hand. There is no scorer identity versioning.

Assets under `evals/cases/grounding/` hold paraphrase cases:

```yaml
case_id: revenue_july_paraphrase_03
question: how much did we recognize in july 2026
expected:
  status: answered
  metric_id: recognized_revenue
  shape: metric_scalar
  time_scope: {month: "2026-07"}
```

Reported metrics: grounding accuracy on answerable paraphrases, refusal
precision and recall on `clarify`, `semantic_gap`, `unsupported`, and
`unsafe` cases, misrouting rate (answered with the wrong metric or slots),
`false_verified_count` (must be zero), fact accuracy against
`expected_facts.yaml` for executed cases, and P50 and P95 latency by path.
Deterministic checks and the retained G2 through G6b contract tests run
offline. The PostgreSQL profile runs when execution contracts change.

## 14. Non-goals for v0.2

Free-text filters, cross-datasource joins, parallel tasks, production
authentication, dashboards, LLM-authored SQL as a default path, best-of-N,
automatic semantic-model mutation, and the probe loop itself.
